# Media Generator AI Workflow — Spec

## O que é

Um sistema de agentes, de uso pessoal e local, que transforma o que eu aprendi (transcrição de vídeo ou arquivo `.md`) em conteúdo para YouTube, LinkedIn e X — e que **aprende com minhas revisões e com o resultado real das publicações** para melhorar as próximas gerações.

O conteúdo é o domínio de exemplo. O produto de verdade é: observabilidade total, controle explícito de contexto e memória procedural. Se o ChatGPT já entrega, não é o foco.

## Como funciona

1. Eu envio um briefing + arquivo e marco as plataformas-alvo (transcrição → YT+LI+X; `.md` → LI+X).
2. O sistema extrai um brief estruturado e monta, para cada agente, um pacote de contexto com: público-alvo da plataforma, regras aprendidas, pesquisa recente sobre a plataforma e exemplos anteriores com meu feedback.
3. Agentes rodam em paralelo por plataforma. Estrategistas de LinkedIn e X recomendam um formato e justificam; eu aprovo; só então o material é gerado.
4. Eu reviso o pacote item a item. Rejeitei algo → escrevo o porquê → só aquele item é regenerado.
5. Depois de publicar, escrevo em texto livre como o conteúdo performou. Um agente extrai regras ("evite X no LinkedIn", "títulos com Y funcionam"), eu aprovo, e elas passam a valer nas próximas runs. Regra contradita não some: fica "contestada" e dispara nova pesquisa.

## Entregas por plataforma

- **YouTube:** 3 títulos com ângulos distintos, 2 thumbnails 16:9, descrição SEO, 15+ hashtags.
- **LinkedIn:** Post, artigo + capa, ou carrossel + copy + 5 Hashtags — formato recomendado pelo agente, aprovado por mim.
- **X:** post, thread ou visual, com CTA para YouTube ou LinkedIn.
- Blocos de código do `.md` viram imagens estilizadas (HTML → PNG), sem o LLM reescrever o código.

## Pontos de decisão humana

Foto/consentimento para thumbnail · formato LinkedIn · formato X · review do pacote · aprovação de cada regra aprendida.

## Memória

- **Curto prazo:** state da run (LangGraph + checkpoint em Postgres).
- **Procedural:** regras de como fazer, sempre aprovadas por mim. Todo artefato, versão, feedback de review e feedback pós-publicação
- **Semântica:** públicos-alvo por plataforma + pesquisa web (Tavily/Firecrawl), renovada a cada 14 dias ou quando uma regra é contestada.
- **Episódica:** Revisões e informações de quando um conteúdo foi muito bem ou muito mal

## Observabilidade

Cada nó grava: prompt e versão, modelo, tokens, custo, latência, o contexto exato que recebeu, saída, erro e decisões humanas. Acesso via CLI.

## Stack

Python · LangGraph (orquestração: grafo, state, fan-out, `interrupt()`, checkpoint) + LangChain (nós individuais via `with_structured_output`, e `create_agent` **só** nos nós de research que precisam de tool loop) · OpenRouter (texto e imagem) · Postgres + pgvector · FastAPI + SSE · React · Playwright · Tavily + Firecrawl.

## Fora do MVP

Vídeo em qualquer plataforma · publicação/agendamento · transcrição automática · chat livre com o sistema · tela de memória · multiusuário.

## Ordem de construção

A regra que ordena tudo: **a UI é a última coisa**. Ela é uma janela para o sistema, não o sistema. Enquanto a memória e a observabilidade não estiverem provadas por CLI, não existe nada para a UI mostrar.

1. **Fundação + um agente completo, ponta a ponta, sem UI.**
   Postgres + migrations, `Agent` base, tracer (`steps` com prompt_version, tokens, custo, latência, `context_pack`), `ContextPack` com allowlist, `memory_loader` com seeds, CLI mínima.
   Um único grafo linear: `ingest_context → memory_loader → li_strategist (interrupt) → li_post → review (interrupt) → finalize → episódica`, já com o **loop de regeneração real** (`regen_targets` no state). É aqui que se descobre a dificuldade de verdade do projeto.
   *Por que primeiro:* sem isso não há memória nem trace, e todo o resto é conteúdo descartável.

2. **Aprendizado com regras.**
   `learning_graph`, regras procedurais com HITL de aprovação, contradição → `contested`, `episodic.search`.
   *Por que agora:* é o passo em que o projeto deixa de ser um gerador de conteúdo e passa a ser o produto descrito na §"Memória".

3. **Demais agentes e plataformas.**
   LinkedIn completo (artigo, carrossel + Playwright), X, YT (+ imagem OpenRouter + HITL de foto) e, por último neste passo, o **fan-out paralelo real** com múltiplos interrupts simultâneos e resume por ID.
   *Por que depois:* paralelismo multiplica o custo de debug. Ele só entra quando um caminho único já funciona.

4. **Pesquisa web.**
   `research_graph` com `create_agent` (Tavily + Firecrawl), TTL de 14 dias, contestação disparando refresh.
   *Por que depois:* é a camada mais ruidosa e cara; ela depende de a memória procedural já existir para ter o que invalidar.

5. **UI.**
   React + SSE, cards de interrupt, review, feedback pós-publicação.
   *Por que depois:* nesse ponto a API já está estável e a UI só desenha estado que já existe e já é observável por CLI.

6. **Fase 2** — evals por agente, OpenTelemetry, estrategista de plataformas, tela de memória.
